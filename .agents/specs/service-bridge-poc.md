# Service Bridge POC Specification

- Status: proposed
- Owner: TBD
- Related decision: [ADR 0001](../decisions/0001-electron-style-service-bridge.md)

## Purpose

Prove that the same typed React application API can communicate with a standalone Go service through Tauri in desktop mode and HTTP in remote-development mode without leaking transport details into feature components.

The CRUD domain exists only to exercise this communication model. Domain sophistication is not an objective.

## Electron-to-Tauri mapping

| Electron concept | POC equivalent | Responsibility |
| --- | --- | --- |
| Renderer feature code | React feature code | Presentation and interaction only |
| Preload `contextBridge` facade | TypeScript `TaskCoreClient` | Narrow, typed methods such as `tasks.list()` |
| `ipcRenderer.invoke` | `DesktopTransport.invoke()` using Tauri `invoke` | Asynchronous request/response |
| IPC channel name | Versioned operation name | Closed capability such as `tasks.create` |
| `ipcMain.handle` | Rust `service_invoke` command | Privileged validation and forwarding boundary |
| Main-process backend module | Standalone Go service | Domain behavior and persistence |
| `webContents.send` through a preload wrapper | Typed Tauri event or channel wrapper | Backend-initiated notification when required |
| Electron sender validation | Tauri capability plus Rust validation | Limits the calling webview and allowed operations |

`TaskCoreClient` is an architectural boundary, not a security boundary. Tauri capabilities, the Rust command, and Go validation provide the security enforcement.

## TypeScript API

React components receive the `TaskCoreClient` from `packages/node/task-core-library` and do not import `@tauri-apps/api` or call `fetch` for application operations. A future application-wide client may compose this task client with system and public-configuration clients without moving task contracts back into the app.

```ts
export interface TaskCoreClient {
  tasks: {
    list(query?: ListTasksQuery): Promise<Task[]>;
    get(id: string): Promise<Task>;
    create(input: CreateTaskInput): Promise<Task>;
    update(id: string, input: UpdateTaskInput): Promise<Task>;
    delete(id: string): Promise<void>;
  };
}
```

The application passes `DesktopTransport` or `HttpTransport` to `createTaskCoreClient` at composition time. Tests and the current UI preview may inject an in-memory implementation.

## Wire envelope

All values crossing the bridge must be JSON-compatible data transfer objects. Do not send class instances, functions, platform objects, database types, or raw errors.

Request:

```json
{
  "protocolVersion": 1,
  "requestId": "01K...",
  "operation": "tasks.create",
  "payload": {
    "title": "Prove the bridge"
  }
}
```

Successful response:

```json
{
  "protocolVersion": 1,
  "requestId": "01K...",
  "ok": true,
  "data": {
    "id": "01K...",
    "title": "Prove the bridge",
    "status": "todo"
  }
}
```

Failed response:

```json
{
  "protocolVersion": 1,
  "requestId": "01K...",
  "ok": false,
  "error": {
    "code": "VALIDATION",
    "message": "The request is invalid",
    "fieldErrors": {
      "title": "Title is required"
    }
  }
}
```

Rules:

- `protocolVersion` is required and rejected when unsupported.
- `requestId` is generated by the TypeScript client and reused as the correlation ID through Rust and Go.
- `operation` is a closed enum, not an arbitrary route, command, or URL.
- `payload` and `data` are operation-specific and validated against the canonical schema.
- Times use RFC 3339 UTC strings; IDs and enums are strings; absent and `null` retain distinct meanings.
- Error codes are stable and machine-readable. Stack traces, SQL errors, service addresses, and secrets never cross into the UI response.
- Request bodies are limited to 64 KiB and encoded responses to 512 KiB in the initial Go implementation.

## Desktop lifecycle

1. Rust generates a cryptographically random bearer token.
2. Rust starts the bundled Go sidecar with loopback binding, port `0`, its database/config paths, and the token supplied through a child-only environment value or inherited pipe.
3. Go binds the assigned port and emits exactly one JSON readiness message on stdout containing the address and protocol version.
4. Rust validates readiness and retains the child handle, address, and secret in managed state.
5. `service_invoke` accepts a bridge request, validates its envelope and operation, applies a timeout, adds service authentication, and posts it to the fixed Go endpoint.
6. Rust validates the service response envelope before returning it to TypeScript.
7. On application exit, Rust requests graceful shutdown and then terminates the child if it does not stop within a bounded timeout.

The Go service writes logs to stderr. Unexpected sidecar exit transitions the bridge to an unavailable state and produces a stable `SERVICE_UNAVAILABLE` error; silent automatic restart is out of scope for the first POC.

## Remote-development mode

The browser uses `HttpTransport` to submit the same request envelope to the same Go endpoint. Remote mode must be explicitly enabled and must not inherit the desktop sidecar token.

Before binding beyond loopback, remote mode must have:

- an explicit bind-address setting;
- a separate development access token;
- an origin allowlist;
- startup output that clearly identifies exposed URLs;
- a documented warning that it is for development only.

## Events and streams

Unary asynchronous calls are sufficient for the CRUD proof. The POC may emit a typed `service.statusChanged` Tauri event for `ready`, `unavailable`, and `stopped` states.

If later work requires progress or high-volume ordered data, add a typed Tauri channel. Do not use global untyped events for request responses.

## Acceptance criteria

- The UI completes the same create, list, update, and delete flow through both desktop and HTTP transports.
- React feature modules contain no direct Tauri or backend HTTP calls.
- A contract test runs identical success and failure fixtures against both transports.
- Unknown operations, malformed payloads, unsupported protocol versions, oversized messages, and invalid tokens are rejected.
- A Go validation error arrives as the same typed `AppError` in both modes.
- One request ID can be followed through frontend, Rust, and Go logs.
- Desktop startup waits for Go readiness and reports a bounded, typed failure when the service cannot start.
- Closing the Tauri application stops the child service.
- The desktop service listens only on loopback and cannot be called without the per-launch secret.
- The browser-safe configuration operation never returns service secrets or database paths.
- Packaged builds include the correct Go sidecar for every supported target.

## Out of scope

- Multiple backend services.
- Service discovery.
- Automatic sidecar restart or supervision beyond clean shutdown.
- Offline synchronization or multiple writers across machines.
- Streaming data beyond one small lifecycle-status demonstration.
- Supporting .NET, Node.js, Bun, or Deno implementations in the first POC.

## Unresolved questions

- Startup and per-operation timeout values.
- Whether the readiness token should travel through an inherited pipe rather than a child-only environment value.
- Whether remote development needs TLS when used outside a trusted local network.
